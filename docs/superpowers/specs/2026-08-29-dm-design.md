# DM (mensagens diretas) — design

## Contexto

`DMView`/`ChatThreadView` já existem com UI completa (lista de conversas,
thread, bolhas, campo de envio) mas rodam 100% em memória sobre
`DMConversation.sample` — hoje `conversations = []` fixo, sem tabela, sem
Supabase. `UserProfileView` já tem um botão "Mensagem" que constrói uma
`DMConversation` vazia e abre o `ChatThreadView` — é o ponto de entrada
natural pra iniciar uma conversa nova.

Esta spec foi escrita sem diálogo interativo (sessão noturna, decisões
delegadas) — decisões de produto abaixo estão marcadas como **Ruling**.

## Objetivo

Mensagens diretas reais entre dois usuários, persistidas no Supabase,
substituindo o estado em memória sem mudar o visual já aprovado.

## Escopo

- Tabela `conversations` (par de usuários) + `messages` (texto, autor,
  conversa, timestamp)
- Buscar lista de conversas do usuário logado, ordenada pela mensagem mais
  recente
- Abrir/criar conversa a partir do perfil de outro usuário
- Enviar e listar mensagens de uma conversa
- Busca por username na lista de conversas (já existe na UI, só precisa
  filtrar dado real)

## Fora de escopo (Ruling)

- **Tempo real (Realtime/push)**: fica pra depois — reabrir a conversa
  ou dar pull-to-refresh atualiza. Simplicidade > polimento agora.
- **Filtros "Primary/General/Requests"**: a UI já tem os chips mas sem
  lógica nenhuma por trás — continuam só visuais (não fazem nada), não é
  este spec que decide critério de spam/request.
- **Indicador de lido/não lido, digitando...**: fora de escopo.
- **Deletar conversa/mensagem**: fora de escopo.

## Dados

### Tabela `conversations`

```sql
create table conversations (
  id uuid primary key default gen_random_uuid(),
  user_a uuid not null references auth.users(id) on delete cascade,
  user_b uuid not null references auth.users(id) on delete cascade,
  last_message_at timestamptz not null default now(),
  created_at timestamptz not null default now(),
  constraint distinct_users check (user_a <> user_b),
  constraint ordered_pair check (user_a < user_b)
);

create unique index conversations_pair_idx on conversations (user_a, user_b);
```

`ordered_pair`/índice único: garante que só existe UMA conversa por par de
usuários, independente de quem iniciou (a app sempre grava com o menor uuid
em `user_a` antes de inserir/buscar — ver Componentes).

### Tabela `messages`

```sql
create table messages (
  id uuid primary key default gen_random_uuid(),
  conversation_id uuid not null references conversations(id) on delete cascade,
  sender_id uuid not null references auth.users(id) on delete cascade,
  text text not null check (char_length(text) between 1 and 2000),
  created_at timestamptz not null default now()
);

create index messages_conversation_idx on messages (conversation_id, created_at);
```

### RLS

```sql
alter table conversations enable row level security;
alter table messages enable row level security;

create policy "participante le suas conversas"
  on conversations for select
  using (auth.uid() = user_a or auth.uid() = user_b);

create policy "participante cria conversa com outro usuario"
  on conversations for insert
  with check (auth.uid() = user_a or auth.uid() = user_b);

create policy "participante le mensagens da propria conversa"
  on messages for select
  using (
    exists (
      select 1 from conversations c
      where c.id = messages.conversation_id
        and (c.user_a = auth.uid() or c.user_b = auth.uid())
    )
  );

create policy "participante envia mensagem na propria conversa"
  on messages for insert
  with check (
    sender_id = auth.uid()
    and exists (
      select 1 from conversations c
      where c.id = messages.conversation_id
        and (c.user_a = auth.uid() or c.user_b = auth.uid())
    )
  );
```

Sem policy de update/delete — mensagens são imutáveis por design (fora de
escopo editar/apagar).

## Componentes

### `SupabaseService` (métodos novos)

- `static func fetchConversations() async throws -> [ConversationSummary]`
  — join `conversations` + `profiles` (do outro participante) + última
  `messages` row, ordenado por `last_message_at desc`
- `static func fetchMessages(conversationId: UUID) async throws -> [DBMessage]`
  — todas as mensagens da conversa, ordenadas por `created_at asc`
- `static func sendMessage(conversationId: UUID, text: String) async throws`
  — insere em `messages`, depois faz update em `conversations.last_message_at`
- `static func startOrFetchConversation(withUserId otherId: UUID) async throws -> UUID`
  — calcula `user_a`/`user_b` ordenando os dois UUIDs (menor primeiro),
  tenta `select` pela chave única; se não existir, insere. Retorna o
  `conversation_id` pra abrir o thread.

### Modelos novos (`Spot It/Spot It/Models/`)

- `ConversationSummary`: `id, otherUserId, otherUsername, otherAvatarUrl, lastMessageText, lastMessageAt`
- `DBMessage`: `id, conversationId, senderId, text, createdAt`

### `DMView`

- `.task`/`.refreshable` chamando `fetchConversations()`, populando
  `conversations` real (mantém a struct `DMConversation` que a UI já usa,
  OU adapta `DMConversation` pra carregar dados de `ConversationSummary` —
  implementador decide o mapeamento mais direto sem duplicar o texto de
  todas as views que consomem `DMConversation`/`ChatMessage` hoje)
- Filtro de busca continua igual, só que sobre dado real

### `ChatThreadView`

- Ao abrir, busca `fetchMessages(conversationId:)`
- Enviar mensagem chama `sendMessage(...)` e recarrega (ou faz append
  otimista local + reconcilia)

### `UserProfileView`

- Botão "Mensagem" chama `startOrFetchConversation(withUserId:)` antes de
  navegar pro `ChatThreadView`, usando o `conversation_id` real — pra isso
  `UserProfileView` precisa saber o `user_id` real da pessoa (hoje só
  recebe `username`/`avatarInitials`/`avatarColors` como strings soltas).
  **Ruling**: `UserProfileView` ganha um parâmetro `userId: UUID` — os
  call sites que a abrem (Feed, Busca, DM) precisam ser ajustados pra
  passar o id real. Isso pode exigir wiring nesses outros arquivos além
  do estritamente "DM" — o implementador ajusta o mínimo necessário pra
  o botão Mensagem funcionar; não é escopo redesenhar Feed/Busca aqui.

## Erros e edge cases

- Enviar mensagem sem `conversation_id` válido → RLS bloqueia, erro
  tratado como toast/mensagem inline igual ao padrão de erro já usado em
  `AuthView`
- Abrir conversa consigo mesmo → não deve ser possível (constraint
  `distinct_users`), mas defensivamente a UI não deve nem mostrar o botão
  "Mensagem" no próprio perfil (isso já é assunto de outra tela, fora de
  escopo mexer aqui — só não quebrar se acontecer)

## Testando

Sem suite automatizada no projeto — self-check manual: duas contas
diferentes (ou a mesma conta simulando via SQL editor), iniciar conversa
pelo perfil, enviar mensagem de um lado, dar refresh do outro lado e
confirmar que aparece.
